# 情感分析可靠性修复设计

## 目标

修复 DeepSeek 请求失败和非 JSON 输出被大量标记为“无法判断”的问题，同时保持现有疑似差评安全边界：任何技术失败都不得触发自动回复。

## 已确认的根因

用户提供的运行数据包含 3209 条评价，其中界面实际可见的 560 条“无法判断”全部来自技术失败：317 条为模型输出无法解析成有效 JSON，243 条为 DeepSeek 请求失败。没有记录是因为评价语义本身无法判断。

当前实现存在四个直接原因：

1. 情感请求只尝试一次，超时、限流和服务端错误不会重试。
2. 模型输出额度只有 220 tokens，且无格式错误修复轮次。
3. 宽松解析器把“模型主动选择 uncertain_skip”和“响应格式无效”折叠成同一个结果。
4. 已回复评价先调用情感分析、后检查回复状态，可能把技术状态写回已回复记录。

## 方案选择

采用“可靠调用层 + 技术状态分离 + 安全阻断 + 历史重分析”的组合方案。

不采用以下方案：

- 单纯降低调用速度：无法修复已经返回但格式错误的响应。
- 最终失败后直接使用现有本地规则自动回复：本地规则对复杂反讽和未覆盖表达可能过于乐观。
- 放宽疑似差评提示词：问题发生在有效分类之前，放宽标准没有作用且会增加误回复风险。

## 架构

### 可靠调用层

新增一个独立的情感分析可靠性模块，负责：

- 将 DeepSeek 错误归类为认证、余额/权限、限流、超时/网络、服务端和未知错误。
- 对限流、超时/网络、服务端错误以及无效 JSON 最多尝试 3 次。
- 对认证、余额/权限错误立即失败，不做无意义重试。
- 使用可注入的请求函数与等待函数，保证重试行为可单元测试。
- 在格式错误后的下一轮追加简短纠正指令，不携带密钥，也不持久化完整模型响应。

`deepseek.js` 继续负责构建提示词和调用 OpenAI 兼容客户端，但把情感请求交给可靠调用层执行。输出上限提高到 500 tokens，温度保持低值。

### 严格解析与兼容解析

`sentiment-core.js` 保留现有宽松 `parseSentimentResponse`，避免破坏已有调用者；新增严格解析入口：

- 没有 JSON 对象、JSON 语法错误、缺少必需字段或标签非法时抛出带类别的格式错误。
- 合法的 `uncertain_skip` 仍作为真实业务分类返回，不会被当作技术故障。

### 技术失败状态

技术失败与四个情感标签分离。评价记录增加以下可选字段：

- `analysisFailed`: 是否为技术失败。
- `analysisErrorKind`: 失败类别，例如 `invalid_json`、`rate_limited`、`network`。
- `analysisError`: 可展示的脱敏错误摘要。
- `analysisAttempts`: 本次分析尝试次数。
- `analysisFailedAt`: 失败时间。

兼容历史数据：当旧记录的 `uncertainReason` 等于“AI判断结果不是有效JSON，跳过自动回复”或“AI情感分析失败，跳过自动回复”时，状态分类器将其视为 `analysis_failed`，无需先迁移文件。

`analysis_failed` 状态必须：

- 在自动回复决策中被阻断。
- 在界面显示“AI分析失败”，而不是“无法判断”。
- 可进入现有批量重新分析流程。
- 在重新分析成功后清空全部技术失败字段。

### 自动回复流程顺序

在 `replyAll` 中，先检查评价是否已经回复、是否不可互动以及是否已有阻断状态，再决定是否调用 AI。已经回复的评价不得再分析，也不得写入情感或技术失败状态。

### 历史数据恢复

沿用现有“重新分析当前账号/全部账号”入口。修复后的版本会识别旧技术失败记录；用户执行预览确认后再应用重分析。成功结果替换旧技术失败状态，失败结果继续保持安全阻断。

## 错误处理

- 401/403：显示 API Key 或权限错误，立即结束本次分析。
- 402 或余额相关错误：显示余额不足，立即结束本次分析。
- 429：指数退避后重试。
- 超时、连接错误、5xx：指数退避后重试。
- 无效 JSON：追加格式纠正指令后重试。
- 三次仍失败：写入 `analysis_failed`，不生成回复、不提交平台。

错误信息不得包含 API Key、Webhook、Cookie 或完整请求头。模型原始输出只允许在服务日志中输出有限长度摘要，不写入评价数据。

## 用户界面

工作台增加“AI分析失败”状态标签和统计项，提示用户可到系统设置重新分析。原“无法判断”仅表示模型明确返回合法的 `uncertain_skip`。

现有设置页的批量重分析按钮继续使用，不新增复杂操作流程。

## 测试策略

按 TDD 覆盖：

1. 严格解析器区分合法 `uncertain_skip` 与无效 JSON。
2. 格式错误、429、超时和 5xx 会重试并最终成功。
3. 401/402 不重试。
4. 三次失败生成技术失败结果，且不可自动回复。
5. 历史技术失败原因被识别为 `analysis_failed`。
6. 已回复评价不会调用情感分析或写入失败状态。
7. 重新分析成功后清除技术失败字段。
8. 后端全量测试、前端 lint、前端生产构建全部通过。

## 验收标准

- 技术失败不再显示为“无法判断”。
- 临时 API/格式故障会自动重试，最多 3 次。
- 最终失败仍不会自动回复。
- 合法的疑似差评和合法的 `uncertain_skip` 行为不变。
- 历史 560 条记录可通过现有重分析流程安全恢复。
- 不修改或打包用户提供的含登录态 ZIP。
